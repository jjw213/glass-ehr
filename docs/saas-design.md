# SaaS 전환 설계 (#150)

Glass HR을 외부 고객사에 판매하는 SaaS로 바꾸는 설계다. 이 문서는 설계만 정한다. **코드·마이그레이션은 바꾸지 않는다.**
결정의 원문은 `docs/DECISIONS.md` 2026-11-26 행이다. 장 번호는 고정이다. 후속 SaaS 이슈가 장 번호로 참조하므로 장을 지우거나 번호를 바꾸지 않는다. 새 내용은 장 안에 절로 더한다.

계층은 **고객사(tenant) → 법인(`enter_cd`) → 사업장(`biz_site`)**이다. 법인 규칙(`docs/tenant-design.md`)은 그대로 두고 그 위에 고객사 단계를 더한다.

## 1. 지금 구조의 문제 (T1~T8)

## 2. 테넌트 구조

### 2.1 계층
- **고객사(tenant)**: 계약·과금·구독·로그인 식별의 단위. 법인 여러 개를 가진다.
- **법인(`enter_cd`)**: 지금과 같다. 사원·근태·급여 데이터의 주인이다. 법인은 고객사 하나에만 속한다.
- **사업장(`biz_site`)**: 지금과 같다. 법인 아래에 있다.
- 법인 코드 규칙(`docs/tenant-design.md` 2장)과 법인별 PK·복합 FK는 그대로 둔다. 고객사 키는 법인 마스터(`enter_company`)에 붙이고, 법인별 테이블에는 넣지 않는다(법인이 고객사를 정하므로 중복이다). 고객사 단위로만 존재하는 데이터(구독·고객사 설정 등)만 고객사 키를 가진다.

### 2.2 고객사 상태
| 상태 | 뜻 | 로그인 | 데이터 |
|---|---|---|---|
| `TRIAL` | 무료체험. 체험 종료일이 있다 | 가능(종료일까지) | 보존 |
| `ACTIVE` | 계약 중 | 가능 | 보존 |
| `SUSPENDED` | 미납·요청 등으로 일시 정지 | 불가(안내 화면) | 보존 |
| `TERMINATED` | 해지 | 불가 | 보존 기간 뒤 파기 |

- 상태가 `TRIAL`(종료일 지남)·`SUSPENDED`·`TERMINATED`면 이미 있는 세션도 다음 요청에서 끊는다. 지금 전환 세션이 요청마다 법인을 다시 확인하는 방식(`DbAuthUserResolver`)을 고객사 상태에도 쓴다.
- 해지 뒤 보존 기간과 파기 방법은 법령 확인이 필요하다. 후속 이슈에서 조문을 확인해 정한다(이 문서에서 정하지 않는다).

### 2.3 고객사 식별
1. **서브도메인 우선**: `acme.glass-hr.example` 처럼 접속 주소로 고객사를 정한다.
2. **없으면 회사 코드 입력**: 공통 주소로 들어오면 로그인 화면에서 회사 코드를 입력한다.
- 고객사는 로그인 때 정해 **세션에만** 둔다. 요청 본문·쿼리로 받지 않는다.
- 다른 고객사 자원은 404로 답한다(존재 여부도 숨긴다).
- 법인 선택은 정해진 고객사의 법인 안에서만 한다. 그러면 T1의 공개 법인 목록은 "그 고객사의 법인"만 보여 주게 된다. 고객사가 정해지기 전에는 법인 목록을 보여 주지 않는다.
- `GROUP_ADMIN` 전환(T2)은 같은 고객사의 법인으로만 한다.

### 2.4 모듈 구독
- 모듈: 인사·조직, 근태, 급여, 평가, 복리후생, 교육, 채용(`AGENTS.md` 모듈 순서).
- 인사·조직은 기본 모듈이다(다른 모듈이 사원·조직 데이터를 쓴다). 나머지는 고객사별로 켜고 끈다.
- 구독하지 않은 모듈은 메뉴에서 숨기고, API는 서버에서 막는다(화면만 숨기지 않는다).
- 구독을 끊어도 데이터는 지우지 않는다(다시 구독하면 이어서 쓴다).

### 2.5 전환 범위
- 운영 서버 데이터는 기존 고객사 하나(`T001`, 이름은 기존 대표 법인 이름)로 옮긴다. 기존 법인(`C001` 등)은 모두 `T001`에 속한다.
- `T001`은 `ACTIVE`이고 모든 모듈을 구독한 상태로 시작한다.
- 마이그레이션은 루프가 알려 주는 번호를 쓰고 한 이슈에 하나만 만든다. 데모 시드·테스트를 함께 고친다.
- 이번 전환에서 하지 않는 것: 과금·결제 연동, 고객사 셀프 가입 화면(5장 순서에서 뒤로 미룬다).

## 3. 법인 설정과 규모별 법령 적용 (방향만)

상세는 다음 묶음 이슈에서 정한다. 여기서는 방향만 둔다.
- 상시근로자 수(T3)와 운영 설정(T6)을 서버 설정(`application.yml`)에서 **법인 설정**으로 옮긴다. 값은 적용시작일을 가진 이력으로 두어 과거 날짜로 다시 계산할 수 있게 한다(`AGENTS.md` 법령 규칙과 같은 방식).
- 규모 기준이 갈리는 조항은 지금처럼 `legal_rate`의 적용 규모 하한과 법인(필요하면 사업장)의 상시근로자 수를 비교해 정한다. 조항별 기준 수치는 `legal_rate`에만 두고 코드에 쓰지 않는다.
- "30인 이상 전제"(`AGENTS.md`)는 고객사마다 규모가 달라지므로 바뀌어야 한다. `AGENTS.md`는 보호된 경로라 바꾸는 시점·문구는 저장소 주인이 정한다.
- 상시근로자 수를 사업장 단위로 볼지 법인 단위로 볼지, 산정 방법을 자동 계산할지 입력할지는 조문 확인과 저장소 주인 결정이 필요하다(다음 묶음에서 질문).
- 고객사 단위 설정(로그인 잠금, 비밀번호 규칙 등)과 법인 단위 설정(규모, 근태·급여 정책)을 나눈다. 둘 다 4장의 "설정 공통 규칙"을 따른다.

## 4. 공통 부품 8개

고객사마다 다른 규칙을 코드 분기 없이 설정으로 받기 위한 부품이다. 각 부품은 고객사·법인 데이터로 두고, 법령 요건은 설정으로 끌 수 없게 한다.

| 번호 | 부품 | 하는 일 |
|---|---|---|
| 1 | 항목·처리방식 | 수당·공제·근태 항목 같은 항목 목록과 각 항목의 처리방식(과세 여부, 통상임금 포함 여부, 절사 단위 등)을 고객사가 정한다. 법정 항목은 기본 제공·삭제 불가 |
| 2 | 대상자 조건 | "어느 사원에게 적용하나"를 조건(법인·사업장·부서·직급·고용형태·근무유형 등)으로 정한다. 항목·신청서·작업 흐름이 같은 조건 형식을 쓴다 |
| 3 | 계산식 | 항목 금액·시간을 정해진 변수와 연산으로 정한다. 금액은 원 단위 정수, 절사·반올림 위치를 식에 명시한다. 법정 계산(가산율, 최저임금 비교 등)은 식으로 덮어쓸 수 없다 |
| 4 | 급여 입력 원장 | 근태 집계·수기 입력·외부 파일 등 급여 계산에 들어가는 값을 사원·월·항목 단위 원장에 모은다. 누가 언제 넣었는지 남긴다 |
| 5 | 신청서 빌더 | 휴가·연장근로·증명서 등 신청서의 입력 칸과 검증을 고객사가 만든다. 결재는 기존 공통 결재 모듈(`docs/approval-line-design.md`)을 쓴다 |
| 6 | 작업 흐름·마감 | 월 근태 마감, 급여 계산·확정 같은 단계와 마감 잠금. 마감 뒤에는 원장을 고치지 못하고 재계산은 기록을 남긴다 |
| 7 | 문서 양식 | 급여명세서·근로계약서·증명서 양식을 고객사가 고친다. 법정 기재 사항은 빠뜨릴 수 없다 |
| 8 | 설정 공통 규칙 | 모든 설정에 공통인 규칙: 적용시작일 이력, 고객사 기본값 → 법인 덮어쓰기, 변경 기록, 시스템 기본값(`system_yn`) 삭제 불가(`docs/common-code-design.md`와 같은 방식) |

## 5. 우선순위와 묶음 순서

앞 묶음이 끝나야 뒤 묶음을 시작한다. 각 묶음은 여러 이슈로 나눈다.

1. **고객사 단계와 분리 보장**: 고객사 마스터·상태, 법인→고객사 연결과 `T001` 이전, 로그인 고객사 식별(서브도메인·회사 코드), 세션 고객사, 법인 목록·`GROUP_ADMIN` 전환을 고객사 안으로 제한(T1·T2). 다른 고객사 자원 404 검사 테스트.
2. **Node 서버 정리(T8)**: 남은 Node 경로를 Spring으로 옮기거나 닫는다. 고객사 분리를 Node 쪽에서 따로 만들지 않는다.
3. **법인 설정과 규모별 법령(T3·T6)**: 3장의 방향을 상세 설계하고 서버 설정을 법인·고객사 설정으로 옮긴다.
4. **키와 역할(T4·T5)**: 고객사별 주민번호 암호화·HMAC 키(키 관리 방법은 이 묶음에서 결정), 고객사별 역할(공통 기본 역할 복사 방식).
5. **모듈 구독**: 구독 테이블, 메뉴·API 차단.
6. **공통 부품(4장)**: 8 → 2 → 1 → 3 → 4 → 6 → 5 → 7 순서(설정 규칙과 대상자 조건이 다른 부품의 바탕이다). 급여 모듈 개발과 맞물린다.
7. **운영 환경(T7)**: 운영 서버·DB 분리, 백업, 배포 방식. 외부 고객사를 받기 전에 끝낸다.
8. **판매 기능**: 무료체험 고객사 생성, 고객사별 채용 사이트, 과금.
