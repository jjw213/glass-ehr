# 신청 결재선 설계안 (#24)

결정: **신청 유형별로 결재선을 관리자가 설정한다**
(2026-11-11 사람 답변, 텔레그램)

대상: 근태의 휴가·연장근로·근태 정정 신청. 이후 교육·복리후생 등 다른 모듈의 신청도 같은 결재 기능을 쓴다.
따라서 결재 기능은 근태 모듈 안이 아니라 **공통 기반(SPEC §0)** 에 둔다.

결재는 회사 내부 승인 절차일 뿐, 법령 요건 판단을 대신하지 않는다.
예를 들어 연장근로 한도·휴가 일수 같은 법령 검사는 각 모듈의 계산 로직이 `legal_rate` 기준값과 근거 조문으로 따로 한다(결재가 승인돼도 법령 검사를 건너뛰지 않음).
이 문서는 구조만 정하며, 법령 수치는 다루지 않는다.

## 1. 기본 개념
| 용어 | 설명 |
|---|---|
| 신청 유형 (`request_type`) | 결재선을 붙이는 단위. 예: `LEAVE`(휴가), `OVERTIME`(연장근로), `ATTENDANCE_CORRECTION`(근태 정정). 다른 모듈은 자기 유형 코드를 추가 |
| 결재선 템플릿 | 관리자가 신청 유형별로 정하는 단계 목록 |
| 결재 단계 | 순서(1, 2, 3…)와 결재자 지정 방식 |
| 결재 문서 | 직원이 신청할 때 생기는 결재 건. 신청 시점의 결재선을 복사(스냅샷)해 들고 간다 |

## 2. 관리자 설정 (결재선 템플릿)
신청 유형마다 템플릿을 하나 둔다. 템플릿은 유효기간 방식(#8과 같은 `[valid_from, valid_to)`, 종료 NULL = 현재)으로 이력을 남긴다.
설정을 바꾸면 기존 행을 고치지 않고 종료일을 넣은 뒤 새 행을 추가한다.

**템플릿 헤더 (초안)**
| 컬럼 | 설명 |
|---|---|
| `template_id` | PK |
| `company_id` | 회사(또는 사업장) |
| `request_type` | 신청 유형 코드 |
| `valid_from`, `valid_to` | 적용 기간 |
| `created_at`, `created_by` | 감사 정보 |

**템플릿 단계 (초안)**
| 컬럼 | 설명 |
|---|---|
| `template_id`, `step_no` | PK. `step_no`는 1부터 |
| `approver_kind` | 결재자 지정 방식 (아래 표) |
| `approver_ref` | 지정 방식에 따른 값(직책 코드, 역할 코드, `emp_id`) |
| `skip_if_self` | 결재자가 신청자 본인이면 이 단계를 건너뛸지 여부 |

**결재자 지정 방식 (`approver_kind`)**
| 값 | 의미 | 결재자를 찾는 방법 |
|---|---|---|
| `DEPT_HEAD` | 신청자 소속 부서장 | 신청일 기준 조직도(#8 유효기간)에서 신청자 부서의 부서장 |
| `UPPER_DEPT_HEAD` | 상위 부서장 | 신청일 기준 상위 부서의 부서장 |
| `POSITION` | 특정 직책 | `approver_ref`의 직책을 가진 사람 |
| `ROLE` | 권한 역할 | `approver_ref`의 역할(예: 인사담당) 중 한 명 |
| `EMPLOYEE` | 특정 사원 | `approver_ref`의 `emp_id` |

- 사람 이름이 아니라 **역할·직책으로 지정하는 것을 기본**으로 해서, 인사이동이 있어도 템플릿을 고칠 필요가 없게 한다.
- 결재자 해석 기준일은 **신청일**(Asia/Seoul)이다. 조직도·직책은 그날 기준으로 찾는다.
- 템플릿이 없는 신청 유형은 신청을 받지 않는다(설정 누락을 조용히 통과시키지 않음).

## 3. 결재 문서와 스냅샷
직원이 신청하면 그 시점의 템플릿으로 결재자를 실제 사람(`emp_id`)으로 풀어 결재 문서에 복사한다.
이후 관리자가 템플릿을 바꿔도 **이미 올라간 결재 문서의 결재선은 바뀌지 않는다.**

**결재 문서 (초안)**
| 컬럼 | 설명 |
|---|---|
| `approval_id` | PK |
| `request_type`, `request_ref` | 신청 유형과 원본 신청 건 ID(휴가 신청 ID 등) |
| `requester_emp_id` | 신청자 |
| `template_id` | 사용한 템플릿 |
| `status` | 문서 상태 (§4) |
| `current_step_no` | 현재 결재 차례 |
| `submitted_at` | 신청 시각(서버 시각) |

**결재 문서 단계 (스냅샷)**
| 컬럼 | 설명 |
|---|---|
| `approval_id`, `step_no` | PK |
| `approver_emp_id` | 신청 시점에 확정된 결재자 |
| `step_status` | `WAITING` / `APPROVED` / `REJECTED` / `SKIPPED` |
| `acted_at`, `comment` | 처리 시각, 의견 |

## 4. 상태 흐름
```
DRAFT ─제출→ IN_PROGRESS ─마지막 단계 승인→ APPROVED
                 │
                 ├─어느 단계든 반려→ REJECTED
                 └─신청자 회수(첫 결재 전)→ WITHDRAWN
```
- 결재는 **순차**로 진행한다(1단계 승인 후 2단계).
- 한 단계라도 반려하면 문서 전체가 반려된다.
- 승인·반려·회수는 모두 **처리 이력 테이블에 추가만** 한다(수정·삭제 없음). 누가 언제 무엇을 했는지 감사 로그로 쓴다.
- 결재 문서가 `APPROVED`가 되면 각 모듈에 알리고, 모듈이 자기 데이터에 반영한다(예: 휴가 사용 확정, 근태 정정 반영).
  결재 기능은 모듈 데이터를 직접 바꾸지 않는다.
- 승인 후 취소(예: 승인된 휴가 취소)는 원 문서를 고치지 않고 **취소 신청을 새 결재 문서로** 올린다.

## 5. 모듈 연결 방식
```
ApprovalService (공통)
  submit(requestType, requestRef, requesterEmpId) → approvalId
  approve(approvalId, approverEmpId, comment)
  reject(approvalId, approverEmpId, comment)
  withdraw(approvalId, requesterEmpId)

ApprovalCompletionHandler (interface, 모듈마다 구현)
  supports(requestType)
  onApproved(requestRef) / onRejected(requestRef) / onWithdrawn(requestRef)
```
- 근태 모듈은 `LEAVE`, `OVERTIME`, `ATTENDANCE_CORRECTION` 핸들러를 구현한다. 교육·복리후생은 각자 유형 코드와 핸들러만 추가하면 된다.
- 권한 확인: 결재자는 자기 차례인 단계만 처리할 수 있다. 신청자는 자기 문서만 회수할 수 있다.

## 6. 테이블·마이그레이션
- 결재선 템플릿·결재 문서 테이블은 사원·부서 테이블이 생긴 뒤 결재 구현 이슈에서 만든다.
- 이번 이슈는 결정 기록만 하며, **마이그레이션 번호를 사용하지 않는다.**

## 7. 테스트 항목 (구현 이슈에서)
- 템플릿 유효기간: 설정 변경 전날 신청 / 변경 당일 신청이 각각 옛 템플릿·새 템플릿을 쓰는지
- 스냅샷: 신청 후 템플릿 변경·부서장 교체가 진행 중 문서에 영향을 주지 않는지
- 결재자 해석: `DEPT_HEAD`·`UPPER_DEPT_HEAD`·`POSITION`·`ROLE`·`EMPLOYEE` 각각, 신청일 기준 조직도 사용
- 신청자가 부서장인 경우 `skip_if_self` 동작
- 순차 진행: 2단계 결재자가 1단계보다 먼저 처리하려 하면 거부
- 반려 시 문서 전체 반려, 이후 단계는 처리 불가
- 회수: 첫 결재 전에는 가능, 이후에는 불가
- 템플릿이 없는 신청 유형은 신청 거부
- 처리 이력이 추가만 되는지(수정·삭제 불가)

## 8. 아직 정하지 않은 것 (구현 이슈에서 질문)
- 결재자 부재 시 대결(대리 결재)·위임을 지원할지, 지원한다면 위임 기간·권한 범위
- 결재자를 찾지 못할 때(부서장 공석 등) 처리: 상위 부서장으로 올림 / 인사담당에게 넘김 / 신청 거부
- `ROLE` 지정 시 역할자 여러 명 중 누가 결재하는지(아무나 한 명 / 전원)
- 병렬 결재(합의)·참조자·전결 규정(조건에 따라 단계 생략, 예: 휴가 1일 이하는 부서장 전결)이 필요한지
- 같은 신청 유형 안에서 조건별(부서·고용형태·일수 등)로 결재선을 다르게 둘지
- 일정 기간 미처리 시 알림·자동 처리 여부
- 회수 가능 시점을 "첫 결재 전"보다 넓힐지
- 설정 단위를 회사로 할지 사업장으로 할지(#9 사업장코드와 연계)
