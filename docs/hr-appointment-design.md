## 2. 테이블 (V014__hr_appointment.sql)
- `hr_appointment`: 발령번호(`appt_no`, 유일), 유형, 대상 사원, 발령일, 이전/이후 값(소속·직급·직책·재직상태), 사유, 휴직 시작·종료 예정일, 확정 여부(`confirmed_yn`)·확정일시.
- 발령번호: `AP-등록연도-6자리 순번`. 순번은 시퀀스 `hr_appointment_no_seq`에서 받아 연도와 상관없이 늘어난다. 롤백하면 빈 번호가 생길 수 있다.
- 재직상태: `ACTIVE`(재직)·`ON_LEAVE`(휴직)·`RETIRED`(퇴직). 사원 테이블에는 아직 재직상태 컬럼이 없다.
- 발령 유형 공통코드 `APPOINTMENT_TYPE`: HIRE(입사)·TRANSFER(전보)·PROMOTION(승진)·TITLE_CHANGE(직책)·LEAVE(휴직)·RETURN(복직)·RETIREMENT(퇴직). 로직이 코드값을 참조하므로 화면에서는 이름·정렬·사용 여부만 바꾼다.

## 3. 유형별 규칙 (AppointmentService)
| 유형 | 바꾸는 항목 | 재직상태 | 그 밖 |
|---|---|---|---|
| HIRE | 소속·직급(필수)·직책(선택) | → 재직 | 발령일 = 입사일. 사원마다 한 건. 이전 값 없음 |
| TRANSFER | 소속(필수, 지금과 달라야 함) | 그대로 | 부서는 발령일에 존속하고 폐지(예정)가 아니어야 함 |
| PROMOTION | 직급(필수, 지금과 달라야 함) | 그대로 | |
| TITLE_CHANGE | 직책(비우면 해제, 지금과 달라야 함) | 그대로 | |
| LEAVE | — | 재직 → 휴직 | 휴직 시작일 ≥ 발령일, 종료 예정일 ≥ 시작일 |
| RETURN | — | 휴직 → 재직 | |
| RETIREMENT | — | → 퇴직 | |

- 유형이 바꾸지 않는 항목은 이전 값을 그대로 옮긴다. 그 항목에 다른 값을 보내면 400.
- 이전 값: 소속·직급·직책은 사원 행의 현재 값, 재직상태는 발령일까지 **확정된** 다른 발령 중 마지막 것(발령일 → 확정일시 → ID 순)의 이후 재직상태. 그런 발령이 없으면 사원 퇴직일 기준(퇴직일 당일까지는 재직).
- 이전 값은 등록·수정·**확정** 때마다 다시 채우고 규칙을 다시 검사한다.
- 확정된 발령은 수정·삭제·재확정 불가(409). 미확정 발령은 수정·삭제 가능.
- 쓰기는 사원 행을 먼저 잠그고(`SELECT ... FOR UPDATE`) 발령 행을 잠가 다시 읽는다(근로계약과 같은 방식).

## 6. 사원 정보 반영·미래 발령·취소 발령 (#59, V019)
근거 조문은 1장과 같다(2026-11-14에도 law.go.kr 자동 조회가 되지 않아 원문 미확인). 취소 발령에도 사유가 필수다(근로기준법 제23조 제1항). 법정 수치는 쓰지 않는다.

### 6.1 이력 계산 (`AppointmentHistory`)
- 이력 = 확정된 발령 중 취소 발령이 아니고, **확정된** 취소 발령으로 되돌려지지 않은 것. 순서는 발령일 → 확정일시 → ID(같은 날 여러 발령은 먼저 확정한 것부터 쌓임).
- 기준일 값 = 기준일(당일 포함)까지의 이력 중 마지막 발령의 이후 값. 미래 날짜 발령은 그날부터 반영된다.
- 기준일까지 이력이 없으면 가장 앞선 확정 발령(취소된 것 포함)의 이전 값, 확정 발령이 없으면 사원 행 값(재직상태는 퇴직일 다음 날부터 퇴직). 입사일 전은 값 없음(API 404).
- 발령 등록·수정·확정 때의 이전 값(3장)도 이제 사원 행이 아니라 발령일 기준 이력 값이다.
- 확정 순서 규칙: 이미 확정된(취소 안 된) 발령보다 **앞선 날짜**의 발령은 확정할 수 없다(409, 뒤 발령의 이전 값이 어긋나므로). 같은 날짜는 된다.

### 6.2 사원 정보 반영
- `employee.emp_status`(V019, ACTIVE·ON_LEAVE·RETIRED)를 추가했다.
- 사원 현재 소속·직급·직책·재직상태는 `EmployeeRepository.applyAppointment`(UPDATE 쿼리) 하나로만 바뀐다. 엔티티 컬럼은 `updatable = false`, 사원 수정 API에는 이 값이 없다.
- 반영 시점: 발령(취소 포함) 확정 직후 같은 트랜잭션에서 오늘(서울) 기준 값으로, 그리고 매일 00:05(서울) `AppointmentDailySync`가 모든 사원을 사원별 트랜잭션으로 다시 맞춘다(미래 발령이 그날 반영됨). 설정: `glassehr.appointment.sync-cron`, `glassehr.appointment.sync-enabled`.
- 퇴직 발령은 재직상태만 바꾼다. 근로자 명부의 퇴직일·사유·보존기한은 기존 퇴직 처리 API(`/api/employees/{id}/retire`)가 그대로 맡는다.

### 6.3 취소 발령
- `POST /api/appointments/{apptId}/cancel {reason}` → 미확정 취소 발령(새 `hr_appointment` 행). 유형·발령일·휴직일은 원 발령과 같고 이전·이후 값은 원 발령의 반대. 연결은 `hr_appointment_cancel`(원 발령당 하나, 유일 제약).
- 확정은 기존 `POST /api/appointments/{id}/confirm`. 확정하면 원 발령과 취소 발령이 모두 이력에서 빠지고 사원 정보가 다시 맞춰진다.
- 제약: 확정된 발령만, 이력의 **마지막** 발령만(뒤 발령부터 차례로), 입사 발령 제외, 취소 발령은 다시 취소 불가. 미확정 취소 발령은 고칠 수 없고(지우고 다시 등록) 지우면 연결도 지운다.
- 응답에 `cancelOfApptId`(취소 발령이면 원 발령)와 `cancelledByApptId`(취소 발령이 붙은 원 발령)를 넣었다.

### 6.4 휴직 기간 조회 (근태 연차·육아휴직용)
- 확정·미취소 휴직 발령마다 `[휴직 시작일, 종료일]`(양끝 포함). 휴직 뒤 처음 나오는 복직·퇴직 발령의 발령일이 종료 예정일 이하이면 그 전날에 끝난다. 휴직 시작 전에 복직하면 기간 없음.
- 재직상태는 복직 발령이 있어야 재직으로 돌아온다(종료 예정일이 지나도 자동 복직하지 않음).
- Java: `AppointmentService.leavePeriods(empId, from, to)`, `leavePeriods(from, to)`(전체 사원). API: `GET /api/employees/{empId}/leave-periods?from=&to=`, `GET /api/leave-periods?from=&to=`. 기간과 겹치는 휴직만 돌려준다.
- 기준일 소속: `AppointmentService.assignmentOn(empId, date)`, API `GET /api/employees/{empId}/assignment?date=`.
